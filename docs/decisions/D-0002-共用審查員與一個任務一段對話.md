# D-0002 共用審查員;一個任務一段對話

| | |
|---|---|
| 狀態 | 提案(沿用範本,待專案成員確認) |
| 日期 | 2026-11-27(沿用範本) |
| 決定者 | 沿用工作流範本;本專案成員確認後改寫 |
| 範圍 | `.claude/agents/`、`.claude/settings.json`、`CLAUDE.md` §3、§5、§9、PR 範本 |
| 相關 | 否決 R-001、R-002 |

## 決定

1. 專案共用兩個 subagent,放在 `.claude/agents/`、進 git:`code-reviewer`(正確性、測試、是否符合 `CONVENTIONS.md`)、`rules-security-reviewer`(`CLAUDE.md`、決策與否決清單、產品紅線、安全、文件同步)。
2. 兩個審查員只讀不改;定義只寫「讀哪些文件、怎麼檢查、怎麼回報」,規則本身留在既有文件。
3. 依改動類型決定跑哪個審查員(`CLAUDE.md` §5 的表),每個 PR 一次;修完不重跑,修正改變了設計或邏輯才再跑。結果摘要寫進 PR 的「審查」一節。
4. 審查員只回報影響正確性、需求、已定案規則或安全的問題,不報風格與優化;用 Sonnet(`model: sonnet`)。
5. 共用的 `.claude/settings.json` 禁止 Claude 讀 `.env`;個人設定放 `.claude/settings.local.json`。
6. 一個任務一段對話:PR 開好、覆寫交接檔後,下一個任務開新對話。

## 理由

- 放在 repo 的 agent,成員 clone 後自動有同一套審查員,隨 PR 演進。
- 通用審查不知道本專案的否決清單與紅線;自訂審查員指向專案文件補上這一塊。
- 規則只留在原本的文件,避免 agent 定義與文件兩處不一致。
- 審查員在獨立情境執行,不受實作過程的推論影響。
- 每個 PR 跑多輪審查,有價值的發現集中在第一輪,後幾輪多是小意見,成本高;審查員被要求找問題就一定會找出一些,照單全收會過度設計。照文件逐條對照是機械性工作,Sonnet 足夠。
- 長對話累積的上下文讓後續任務更貴、更容易被舊推論影響。
