## 決定

1. **建置用 Vite,語言用 TypeScript,不用前端框架。** Vite 與 TypeScript 只在開發時使用,不會散布出去。
2. **影片封裝、讀取用 `mediabunny`。** 處理 MP4 / WebM 的封裝,以及接檔、修剪時讀取錄影。
3. **GIF 用 `gifenc`。**
4. **動態 WebP 不用套件。** 瀏覽器原生把每一格編成 WebP(`OffscreenCanvas.convertToBlob`),再由我們自己的程式組成動態 WebP(RIFF `VP8X` / `ANIM` / `ANMF`)。

## 理由

- **TypeScript:** WebCodecs、MediaRecorder、manifest 的型別多,步驟清單格式又要三邊共用(`CLAUDE.md` §8),型別能在編譯時抓到欄位打錯。
- **Vite:** 打包成靜態檔就能放上 GitHub Pages;之後播放元件 `<step-reel>` 要單獨打包成一支 JS 也方便。
- **不用框架:** 播放元件定為 Web Component(D-0009 第 5 點);錄製頁的規模用不到框架。
- **mediabunny:** 原本的候選 `mp4-muxer`、`webm-muxer` 已在 npm 標記棄用,作者要使用者改用 mediabunny。它也能讀影片,把各步接成一支 MP4 時用得到。
- **gifenc:** 零依賴、程式小,功能已經完成,久未更新的風險可以接受。
- **動態 WebP 自己封裝:** 每一格的編碼由瀏覽器原生處理,容器格式簡單,自己寫可以省掉一個 WASM 套件。

## 否決的方案

| 方案 | 否決原因 | 重啟條件 |
|---|---|---|
| `mp4-muxer`、`webm-muxer` | 已棄用,被 mediabunny 取代 | 無 |
| 不用建置工具,直接寫 ES modules | npm 套件要自己複製進 repo 或從 CDN 載入,也沒有型別檢查 | 無 |
| GIF 改用 `modern-gif` | 多一個依賴;gifenc 已經夠用 | gifenc 出現修不掉的問題時 |
| 動態 WebP 改用 `@jsquash/webp`(WASM) | 套件大(未壓縮約 900 KB);原生編碼可能就夠 | 實測發現原生 WebP 編碼的畫質或大小明顯不夠時 |
